# Решения по промпту

## Источник и контракт

[System-промпт](../app/prompt.py) задаёт роль технического редактора, границу доверия, правила фактов и редакторскую структуру. Пользовательское сообщение содержит отдельный объект `product`. Инструкции внутри паспорта считаются данными. Ссылки не открываются, поиск и внешние инструменты модели не подключены.

Промпт использует явные ограничения, разделение инструкций и данных, контракт и проверку результата. Это соответствует подходам из [руководства OpenAI по промптам](https://developers.openai.com/api/docs/guides/prompt-engineering). [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat) задаёт структуру, но не доказывает истинность содержания.

## Технические факты

Заполненные имена и значения `specs` копируются дословно. Пустое или отсутствующее значение можно извлечь из `description`, только если оно является точным непрерывным фрагментом с условиями и единицами. Локальный валидатор проверяет наличие этого фрагмента. Он не распознаёт произвольную техническую семантику.

Два типичных критичных пропуска, степень защиты и поверка, выводятся явно. Не добавляется произвольный перечень неизвестных параметров. Калибровка не подтверждает поверку, дополнительная услуга не подтверждает состояние экземпляра. Опция не становится частью комплекта, среднее значение не становится гарантированным пределом, погрешность не становится классом точности.

При противоречии требуется `needs_data`, обе версии в предупреждениях и запрос уточнения. Спорный диапазон не используется как подтверждённый поисковый запрос. Дословная строка `specs` при этом остаётся видна для сверки.

## Текст

Описание содержит три абзаца о назначении, важных параметрах и особенностях. Целевой объём от 900 до 1000 символов оставляет запас внутри допустимых 800–1200. Каждое предложение добавляет факт, задачу или условие применения. Повторы назначения, канцелярские обороты и комментарии о подготовке текста запрещены. Полная таблица не должна дублироваться в описании.

Двоеточие и длинное тире запрещены в авторском тексте. Точные технические значения и синтаксис JSON сохраняются. Если известны только название и не более двух характеристик без описания, допустим короткий честный запрос уточнений. Это исключение предотвращает заполнение объёма выдумками.

В описании и блоке менеджера диапазоны записываются словами «от» и «до». Многоточие между числовыми границами отклоняется валидатором. Знаки, границы, единицы и условия сохраняются, исходная таблица остаётся дословной.

## Проверка и исправление

Приложение запрашивает строгий JSON Schema и независимо проверяет ответ. Контролируются схема, длины, абзацы, запросы, повторяющиеся ключи и характеристики, точные значения, новые числа и единицы, часть условий среднего ресурса и пунктуация.

Для исправления содержания в контекст добавляется предыдущий ответ и конкретные ошибки. Всего допускаются две попытки. Ошибки API, сети, отказ модели и обрезанный ответ не запускают автоповтор. В ответе нужен только JSON карточки.

## Что проверено

[Реальные вызовы](model-evaluation.md) охватывают два товара, паспорт без `specs`, почти пустой ввод, противоречие и команду внутри описания. Один результат был отклонён проверкой пунктуации после двух попыток. Повторный отдельный запуск с тем же промптом прошёл с первой попытки. Сервис вернул ошибку и сохранил предыдущую карточку. После обновления редакторских правил оба итоговых примера прошли проверку с первой попытки.

Валидатор находит новые числа и изменённые значения. Редактор дополнительно проверяет, к какому параметру относится каждое значение и сохранены ли условия измерения.
